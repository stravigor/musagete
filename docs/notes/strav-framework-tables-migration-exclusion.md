# `@strav/database` — exclude framework-managed tables from migration diff

**Status:** issue draft, ready to file against [stravigor/strav](https://github.com/stravigor/strav).
**Surfaced by:** musagete slice 002 (Workspace + Space bootstrap), Build-T1 Checkpoint 1.
**Slice 001 precedent:** `docs/notes/strav-parent-fk-uniqueness.md` (deleted after upstream resolution); `docs/notes/strav-pgvector-extension.md` (still open as of 2026-05-09). Pattern reused.
**Severity:** high — would silently break working features in any project that uses `@strav/http`'s `SessionProvider` and runs a migration generated by another slice.

---

## Reproducer

A project registers `@strav/http`'s `SessionProvider` (or any other Strav provider that creates framework-managed tables). On boot, the provider creates its tables in the live database — for `SessionProvider`, that's `_strav_sessions` and `_strav_access_tokens`. These tables have no project-level schema in `database/schemas/` because they are framework-internal.

Some time later, a different slice authors new schemas and runs:

```sh
bun strav generate:migration -m "<message>"
```

The migration generator diffs `database/schemas/*.ts` against the live database. Because the framework-managed `_strav_*` tables exist in the database but have no schema source, the generator classifies them as **orphan tables** and emits drops:

```sql
-- tables/_strav_access_tokens/up.sql
DROP TABLE IF EXISTS "_strav_access_tokens" CASCADE;
-- tables/_strav_sessions/up.sql
DROP TABLE IF EXISTS "_strav_sessions" CASCADE;
```

Plus matching `ALTER TABLE "_strav_access_tokens" DROP CONSTRAINT IF EXISTS "uq__strav_access_tokens_token";` in `constraints/up.sql` and `DROP INDEX IF EXISTS "idx__strav_access_tokens_token_unique";` in `indexes/up.sql`.

The down side is structurally wrong: it tries to recreate the tables (e.g. `ALTER TABLE "_strav_access_tokens" ADD CONSTRAINT "uq__strav_access_tokens_token" UNIQUE ("token");`) without their `CREATE TABLE` parent, because the generator never created them in the first place — `SessionProvider` did.

### Concrete impact

In musagete, applying migration `1778322180966` would silently un-green slice 001's BDD scenarios 4 + 5 (Google + GitHub OAuth) by dropping the OAuth state tables `SessionProvider` reads on every callback, and would break slice 005's session-bound API access once that ships. The user has no schema-level surface to declare "this table is mine, leave it alone" — short of adding a stub schema for every framework table the project uses, which inverts the framework/project ownership boundary.

---

## Expected behavior — proposed fix

`@strav/database`'s migration generator excludes any table whose name starts with the reserved prefix `_strav_` from its diff. These are owned by the framework and managed by their respective providers; the project's `database/schemas/` is not the source of truth for them.

### Implementation surface

- `MigrationGenerator` (or wherever the diff between live-DB introspection and schema registry happens): when computing the orphan set, filter out any table whose name starts with `_strav_`.
- The same filter applies to constraint/index drops on those tables (otherwise the generator emits a `DROP CONSTRAINT` against a table it can't see, defeating the purpose).
- Document the convention in `@strav/database`'s migration docs: "Tables prefixed `_strav_` are framework-managed and excluded from project-level migration diffs."

### Edge case — alternative spellings

If `_strav_` ever turns out to be too narrow (e.g., a future package adopts `_strav_kernel_*` vs. `_strav_http_*`), the prefix can stay shared since it's the framework-namespace marker, not a per-package one. No need for per-package prefixes.

### Edge case — overrides

In the rare case that a project *wants* to manage a `_strav_`-prefixed table itself (e.g., to adjust its schema beyond what the provider does — there's currently no precedent), the project would need to opt in via a config knob. Not needed in v1; design for it later if a use case appears.

## Acceptance criteria

- [ ] A live database containing `_strav_sessions`, `_strav_access_tokens`, or any other `_strav_`-prefixed table does not cause `bun strav generate:migration` to emit `DROP TABLE`, `DROP CONSTRAINT`, or `DROP INDEX` against those tables.
- [ ] `bun strav compare` does not report `_strav_`-prefixed tables as drift.
- [ ] An explicit project-level `defineSchema('_strav_anything', { … })` (which would be unusual but technically permitted) still works — i.e., the exclusion only applies when there is no project schema for that table name.
- [ ] A test under `node_modules/@strav/database/tests/migration_framework_tables.test.ts` asserts the exclusion behavior across the diff path.
- [ ] Migration manifest's `summary.tablesToDrop` count excludes framework tables.
